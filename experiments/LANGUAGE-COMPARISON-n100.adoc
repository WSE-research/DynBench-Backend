= Substitute Ranking by Question Language: RDF2Vec vs Sentence Embeddings, 100/language
:toc:
:toclevels: 3
:sectnums:

_Extends `rdf2vec-optimizations/CONCLUSION.adoc`, `embedding-optimizations/CONCLUSION.adoc` and `CROSS-METHOD-COMPARISON.adoc` -- all three were run on English-heavy samples (English majority, `en 27, ru 14, de 6, uk 3` at n=50; `en 64, ru 58, uk 12, de 12, fr 4` at n=150). This study instead stratifies the evaluation set so every one of DynBench's 5 supported languages (English, German, French, Russian, Ukrainian) is represented with a comparable sample size, to check whether the cross-method verdict and each method's optimized configuration still hold once the language skew is removed._

[abstract]
Sampling ~100 gold-substitution items per language (478 total; French and Ukrainian fall short at 90/88 because the benchmarks contain fewer qualifying records for those languages) and re-running each study's production and optimized configuration shows the two methods diverge more once the sample is language-balanced than the English-heavy studies suggested. RDF2Vec's optimized global model (`global_depth1_fullcorpus`, MRR 0.355) is both the strongest configuration overall and the most *language-robust* one (per-language MRR band 0.334-0.393), while the optimized sentence-embedding config (`bge-large-en-v1.5` on the entity label, MRR 0.287) swings much wider by language (0.227 Russian -- 0.382 French). RDF2Vec leads in 4 of 5 languages; French is the one language where embeddings edge ahead. Both production configurations remain weak in every language, confirming the original optimization verdicts were not an artifact of the English-heavy samples they were derived from.

== What is being compared

Same harness, same gold-substitute metric (MRR / Hits@k of the gold entity within the shared same-type candidate pool), same two methods, but a *stratified* evaluation set instead of a randomly-shuffled one:

* `rdf2vec-optimizations/_prepare_eval_data_stratified.py` samples up to `EVAL_N_PER_LANG` (100) gold pairs *per language* independently (instead of one global shuffle across all languages), so no language can crowd out the others.
* The candidate pools, the local graph for RDF2Vec, and both methods' configurations are otherwise identical to the existing studies -- production and the previously-established best configuration of each method:

[options="header"]
|===
| Method | Configuration | Source study
| RDF2Vec production | `baseline_per_request` (per-request Word2Vec, depth-2, 4 walks) | `rdf2vec-optimizations/run_experiment.py`
| RDF2Vec optimized | `global_depth1_fullcorpus` (one global Word2Vec, depth-1 walks, trained on every node in the local graph) | `rdf2vec-optimizations/CONCLUSION.adoc`
| Embedding production | `model__mMiniLM_baseline` (multilingual-MiniLM, "label, description", cosine) | `embedding-optimizations/run_experiment.py`
| Embedding optimized | `tmpl__bgeLargeEn_label` (`bge-large-en-v1.5`, entity label only, cosine) | `embedding-optimizations/CONCLUSION.adoc`
|===

== Data and harness

* `experiments/rdf2vec-optimizations/_prepare_eval_data_stratified.py` (new) -- per-language stratified sampling; same gold-pair diffing and candidate-pool logic as `_prepare_eval_data.py`, reused via import.
* `experiments/rdf2vec-optimizations/data_lang100/` -- `eval_set.json` (478 items), `node_uris.json` (10,615 unique entities), `local_graph.nt` (362,891 truthy-edge triples, depth 2), `local_graph_stats.json`.
* `experiments/embedding-optimizations/results_lang100/`, `experiments/rdf2vec-optimizations/results_lang100/` -- raw per-item results for each of the 4 configurations above, same JSON schema as the existing studies (`eval_common.aggregate`).
* `experiments/rdf2vec-optimizations/_analyze_by_language.py` (new) -- joins a result file's per-item ranks back to the eval set's `language` field and reports MRR/Hits@k/coverage per language. Joins by *list position*, not by the benchmark's `id` field: DynQALD/DynRuBQ reuse the same id (e.g. `train:31`) across a question's per-language translations, so `id` collides across languages and is not a safe join key -- `run_experiment.py` preserves list order between the eval set and its results, so position is.
* `experiments/language-comparison-n100-by-language.json` -- machine-readable per-language/per-config summary (MRR, Hits@1/5/10, coverage), generated by `_analyze_by_language.py --json`.

=== A live-endpoint throttling note

Both live-query stages (`_prepare_eval_data_stratified.py`, `_materialize_graph.py`) query the public `query.wikidata.org` endpoint. Partway through this run, previously-fast queries (which round-tripped in well under a second before) began timing out at 30s almost universally -- consistent with the endpoint throttling this client after the sustained volume of the data-prep stage (~2,500+ requests). Backing off to `MAT_QUERY_DELAY=1.0` (from the default 0.3s) and `MAT_QUERY_TIMEOUT=15.0` (from 30s) restored a ~95% per-query success rate; both scripts now expose `EVAL_QUERY_TIMEOUT` / `MAT_QUERY_TIMEOUT` / `MAT_QUERY_DELAY` env vars (not present in the original scripts) so future large runs can tune this without editing code. Graph materialization for the 10,615-node / depth-2 scope took ~1.8 hours at this rate.

== Results

|===
| Config | ALL (n=478) | en (n=100) | de (n=100) | fr (n=90) | ru (n=100) | uk (n=88)
| RDF2Vec production (`baseline_per_request`) | 0.188 | 0.187 | 0.220 | 0.166 | 0.173 | 0.196
| Embedding production (`mMiniLM`, label+desc) | 0.240 | 0.193 | 0.237 | 0.345 | 0.171 | 0.267
| Embedding optimized (`bge-large-en` + label) | 0.287 | 0.239 | 0.281 | 0.382 | 0.227 | 0.320
| *RDF2Vec optimized (`global_depth1_fullcorpus`)* | *0.355* | *0.342* | *0.351* | 0.360 | *0.334* | *0.393*
| random baseline | ~0.18 | -- | -- | -- | -- | --
|===

Coverage (fraction of items where the gold substitute was ranked at all): RDF2Vec ~85-93% across languages; embedding methods ~73-87%, both methods lowest for the language they each score worst on (en for embedding coverage, fr for RDF2Vec coverage) -- coverage and ranking quality don't move together here.

== Findings

1. *RDF2Vec's optimized global model is both the strongest configuration and the most language-robust one.* Its per-language MRR spans a tight 0.334-0.393 band, while the optimized embedding config swings from 0.227 (ru) to 0.382 (fr) -- a gap over 2.5x wider. This is consistent with the mechanism: RDF2Vec ranks by graph structure, which carries no language signal, whereas the embedder's input text is always the entity's *English* label regardless of the question's language, so it should be exactly as sensitive to how well individual entities are documented in English as it in fact turns out to be.
2. *Embedding methods have a consistent language bias: French scores highest, Russian scores lowest, in both the production and optimized configuration.* Since the embedded text is always English, this isn't a multilingual-encoder-quality effect -- it more likely reflects that the entities RuBQ (Russian) draws its questions from have thinner or noisier English Wikidata descriptions than the ones DynQALD-fr draws from. This would be worth confirming directly (e.g. label/description non-null rate by source benchmark) before relying on it operationally.
3. *French is the only language where the embedding method (0.382) beats RDF2Vec (0.360)* -- everywhere else RDF2Vec's optimized configuration leads, more decisively than `CROSS-METHOD-COMPARISON.adoc`'s "statistical tie" verdict (which was derived from an n=150 sample that was 43% English). The tie in that study may partly be an artifact of its language mix rather than a property of the methods themselves; a like-for-like statistical (bootstrap) comparison on this stratified set would be needed to confirm the gap here is significant and not remove it as an open question rather than a settled one.
4. *Both production configurations underperform their optimized counterparts in every single language*, confirming the original studies' central conclusions (the per-request RDF2Vec corpus is too small; the production embedding template/model is suboptimal) generalize beyond the English-heavy samples they were originally derived from.

== Caveats carried over

All limitations of the underlying gold metric documented in `rdf2vec-optimizations/README.md` and `CROSS-METHOD-COMPARISON.adoc` apply unchanged here (the gold is a single popularity-matched substitute, not "the" correct one; the metric favors structural/identity matching by construction; coverage was decoupled from ranking via gold-injection). Additionally:

* *No significance testing performed here.* The per-language Ns (88-100) are smaller than the n=150 pooled sample the original studies bootstrap over, and the differences between methods within a language have not been bootstrap-tested. Treat the per-language deltas as suggestive, not confirmed.
* *French and Ukrainian are slightly under-sampled* (90 and 88 vs the 100 target) for the reason above -- unlikely to change the qualitative picture given the gaps involved, but the comparison across languages is not on perfectly equal N.
